# 검증

## 코드 게이트

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy src tests      # strict
uv run pytest -q
```

2026-10-03 결과: ruff 통과, mypy strict 통과(27 파일), pytest 34개 통과(약 4초).
`web` extra가 없으면 `test_web.py`는 건너뛴다.
Python 3.12.3, Linux.

| 테스트 파일 | 확인하는 동작 |
| --- | --- |
| `test_determinism.py` | 같은 seed는 같은 픽셀과 파라미터를 낸다. seed가 다르면 결과도 다르다. variant seed 고정값과 경로 구분자 무관성. 프로세스 1개와 2개의 출력 파일이 바이트 단위로 같다 |
| `test_dimensions.py` | 출력 크기가 `scanner.dpi`를 따른다. 파일 DPI로 물리 크기를 정한다. 투명 배경은 종이가 된다. 잘못된 DPI 정보는 해결 방법을 담은 오류를 내고 파일을 쓰지 않는다 |
| `test_presets.py` | 필수 프리셋 5개. `office-clean` 회전 0.1° 이하. office 계열에서 단색 검정·2 px 선·연회색 면·흰 종이가 구분된다. 모든 프리셋에서 메타데이터의 좌표 변환으로 스캔본을 원래 위치로 되돌리면 원본과 상관계수 0.95 초과(좌표 기록 검증) |
| `test_pdf.py` | PDF 각 페이지가 따로 처리되고 쪽 번호가 붙은 이름·서로 다른 seed·`page` 메타데이터를 갖는다. 300 dpi 페이지가 600 dpi로 렌더링되어 300 dpi로 스캔된다. 여러 쪽 PDF를 파일 하나로 출력하면 오류이고, 1쪽 PDF는 된다. 열 수 없는 PDF는 계획 단계에서 오류다 |
| `test_web.py` | 업로드 결과의 variant seed가 CLI와 같고 이미지·JSON·원본 미리보기를 받을 수 있다. PDF는 고른 쪽만 처리하고 범위 밖 쪽은 400이다. 잘못된 `--set`은 실제 검증 메시지로 400을 낸다 |
| `test_pipeline.py` | 빈 종이에 질감이 있다(완전한 흰색이 아니다). 프린터와 스캐너 흐림이 각각 따로 작용한다. JPEG는 한 번만 인코딩되고 품질이 기록된다. `--set`·`extends`·검증 오류. CLI의 이름 규칙, dry-run, 덮어쓰기 거부, 이름 충돌, 입력 안 출력 거부, 읽을 수 없는 파일 보고와 종료 코드 1. 여백을 주고 기울이면 배경판이 종이보다 어둡게 보이고 종이 경계 바로 밖에 그림자가 생긴다 |

## 현실성 점검 (실물 비교 없음)

비교 쌍이 없으므로([ADR-001](../decisions/ADR-001-v01-scope.md)) 일반적인 사무용 복합기
컬러 300 dpi JPEG 스캔에서 알려진 특성을 기준으로 삼았다. 기준은 흰 배경 245~253과
미세한 질감, 본문 검정 획 중심 20~45, 1 px 선이 회색으로 남는 것이다. 이 값으로
`samples/`를 육안과 수치로 점검했다. 아래 값은 **실측 보정이 아닌 추정치에 대한 점검**이다.

`memo_005.png`, seed 7. 획 중심은 9~11 pt 줄의 국소 최솟값 중앙값(0~255)이다.

| 프리셋 | 흰 배경 평균 | 흰 배경 표준편차 | 9~11 pt 획 중심 |
| --- | --- | --- | --- |
| office-clean | 252 | 0.1 | 20 |
| office-medium | 251 | 0.6 | 23 |
| office-adf | 251 | 0.6 | 24 |
| office-aged | 235 | 1.8 | 58 |
| ocr-stress | 237 | 0.5 | 93 |

육안 점검 결과:

- office 계열에서 8~13 pt 한글, 작은 숫자, 1 px 엑셀 선, 연회색·연파랑 음영, 붉은 도장,
  QR 모양 패턴의 모듈이 모두 구분된다. 글자는 원본보다 약간 부드럽고 회색 기가 있다.
- `office-aged`는 대비가 낮고 배경이 어둡고 얼룩지며 가장자리가 거칠다. 단순 노란
  색조가 아니다.
- `ocr-stress`는 기울기, 흐림, 낮은 대비, 가로 띠, JPEG 손실이 눈에 띄지만 사람은 읽을 수 있다.
- 구현 중 결함 1건을 찾아 고쳤다. 가장자리 이동이 얇은 선의 테두리를 단색 면보다
  진하게 만들었다. 지금은 흡수율을 단색 농도로 제한한다([PIPELINE](../architecture/PIPELINE.md)).

## 성능

A4 300 dpi 입력 1장(working 600 dpi, 출력 300 dpi JPEG): 약 5.4~5.9초, 최대 메모리
약 2.4 GB. 측정 시 서버 부하는 12코어에 load average 약 30이었으므로 한가한 기계에서는
더 빠를 수 있다.

같은 조건에서 5장 일괄 처리 시간은 `--workers 1`이 26.7초였다. `--workers 5`는 41초로
오히려 느렸고, 커널(sys) 시간이 크게 늘었다. 큰 배열을 반복해서 할당하는 비용이
프로세스 사이에서 경합한 것으로 보인다. glibc의 `MALLOC_MMAP_THRESHOLD_`를 키우면
`--workers 2`가 17.7초로 빨라졌다. 바쁜 서버에서 잰 값이라 확정적이지 않다.
병렬 처리 시 프로세스당 메모리 2.5 GB와 물리 코어 절반 정도를 권장한다.

## 확인하지 못한 것

- **Windows 실행.** 이 환경은 Linux다. Windows 호환을 위해 프로세스 생성은 `spawn`
  방식을 쓰고, 한글 경로 때문에 입출력은 Pillow로 하며, 경로는 `pathlib`으로 다룬다.
  `spawn` 경로는 Linux 테스트로 확인했다. 실제 Windows 실행은 아직 하지 않았다.
- **Python 3.11.** 지원 대상이지만 3.12에서만 실행했다.
- **실물 복합기와의 일치.** v0.2 캘리브레이션 전까지는 추정이다.
