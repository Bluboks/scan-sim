# ADR-005: PDF 입력

- 상태: ACCEPTED
- 날짜: 2026-10-03
- 결정 주체: 소유자(PDF 입력 추가) · 에이전트(위임, 구현 방식)

## 배경

ADR-001은 PDF를 v0.2로 미뤘다. 2026-10-03 소유자가 PDF 입력을 요청했다. 명세 §27은
PDF를 페이지별로 600 dpi 래스터화한 뒤 처리하고, 렌더러로 PyMuPDF를 권했다.

## 결정

- 소유자 결정: PDF를 입력으로 받는다. 출력 형식(이미지)은 바꾸지 않는다.
- 렌더러는 PyMuPDF 대신 `pypdfium2`(PDFium, Apache-2.0/BSD)를 쓴다.
- 페이지는 working DPI(기본 600)로 바로 렌더링한다. 벡터 글자가 확대 보간 없이 실제
  600 dpi 가장자리를 갖는다. 흰 종이 배경을 깔고, 양식 필드와 주석도 그린다. 텍스트
  레이어는 남지 않는다.
- 페이지 하나가 독립된 입력이다. 출력 이름은 `<stem>_p<쪽 3자리>_scan_<variant 4자리>`,
  seed 키는 `<상대 경로>#p<쪽>`이다(ADR-003 보완). 이미지 입력의 이름과 seed는 그대로다.
- CLI는 모든 페이지를 처리한다. 출력이 파일 하나인 경우는 1쪽짜리 PDF만 허용한다.
  웹 화면은 한 번에 고른 한 페이지만 처리한다.
- 페이지 수는 작업 계획 단계에서 센다. 열 수 없는 PDF(손상, 암호)는 계획 단계에서
  오류로 멈춘다. 페이지 크기가 `input.max_page_mm`을 넘으면 렌더링하기 전에 오류를 낸다.
- 메타데이터에 `page`(이미지는 `null`)를 추가하고, `input_dpi.origin`은 `pdf-render`다.

## 이유·trade-off

PyMuPDF는 AGPL-3.0 또는 상용 라이선스라 도구를 배포하거나 서비스에 넣을 때 제약이
생긴다. PDFium은 Chrome의 PDF 엔진이고 Windows용 wheel도 있다. 대신 PyMuPDF의 PDF
쓰기 기능이 없으므로, 나중에 PDF 출력을 하려면 별도 방법(예: Pillow로 이미지 PDF
조립)이 필요하다.

계획 단계에서 페이지를 세므로 손상된 PDF 하나가 일괄 처리 전체를 멈춘다. 대신 출력
목록과 이름 충돌을 처리 전에 확정할 수 있다. 오류 메시지가 파일을 가리키므로 그 파일을
빼고 다시 실행하면 된다.

## 후속

- PDF 출력(`--pdf-output pdf`, raster-only PDF)은 아직 범위 밖이다.
- 페이지 범위 선택(`--pages`)은 요청이 있으면 추가한다.
